# Tungstate Build Syllabus

Extracted from `DESIGN.md` §11. Each slice gets its own brief under `docs/slices/`.

## 11. Build order

Each slice is small enough to finish in days, ends in something runnable, and teaches one or two Rust concepts. **DECIDED: drain first.** The user is new to Rust, so slices 0–9 are entirely synchronous; `tokio` first appears in slice 10.

### How a slice runs (changed 2026-09-09)

Originally the user wrote the code and Claude reviewed. Writing Rust as a newcomer proved to be the slow step, and the user is shipping a product, so that step moved to Claude. Everything the user is fast at stayed with them.

1. Claude writes a **slice brief**: goal, runnable outcome, the design decisions and their alternatives, acceptance criteria, and the tests that must pass. The brief is the spec.
2. Claude implements it, and does not stop until `build`, `test`, `clippy -D warnings`, `fmt --check` and CI on all three platforms are green.
3. Claude writes a **tour** at `docs/slices/NN-tour.md` walking the shipped code and explaining each Rust concept where it appears. Source comments stay short and load-bearing; the teaching lives in the tour.
4. The user reads the tour and the diff, then says go. Claude stops after every slice.

Claude still asks before choosing on anything non-obvious. No silent design calls.

The "Teaches" column below is adjusted for a Rust newcomer: ownership and borrowing in slice 1, `Result` and error design in slice 1–2, traits and trait objects in slice 1, enums as state machines in slice 3, threads and channels in slice 3–4, lifetimes when the parser needs them in slice 5.

**DECIDED (NAS is reached via Finder mount and via FTP):** the first drain (slice 3) targets the Finder-mounted volume through the local backend with network-mount detection. Slice **4b** then widens the seam — a link end becomes a connection plus a path inside it — and **4c** adds FTP itself, with `Capabilities` flags for FTP (no native checksum, non-atomic rename on some servers) and the same drain over `ftp://`. **4e** puts connections in the desktop app. Slice 12 then shrinks to WebDAV and S3, since FTP landed in 4c and SFTP is hand-rolled (DESIGN.md §6). FTP has no server-side checksum, so `readback` is the recommended (not default) verify level for FTP links, and the CLI says so when such a link is created.

Slices 0–4g are "v0.1: the drain works and I trust it, over a mount and over FTP." Slices 5–9 are "v0.2: governance." 10–14 are "v0.3: daemon and UIs."

**Licence and hosting (DECIDED):** `MIT OR Apache-2.0`, public GitHub repository, Rust ecosystem convention.



## Scope changes made during the build

- **A transfer test asserted on thread scheduling, and macOS CI caught it (2026-09-22).** `largest_first_reclaims_the_most_space_soonest` recorded the order files were *started* in and compared it with the largest-first queue. The queue is right, but with several workers which one calls `starting` first is the scheduler's choice, so the test was a coin flip that had landed the right way up for months. It now runs with `parallel(1)`. The rule it broke is already written down: tests must not depend on iteration order or timing.

- **Slice 8 is the redesign, and dedup becomes 8b (2026-09-22).** The window was rebuilt around `folder learn` and `folder compare` under the number 8, which the table had given to dedup. Dedup keeps its scope and moves to 8b. Older entries and slice docs that say "slice 8" for dedup, `on_duplicate` or `Trash` mean 8b. The redesign also needed one Rust change after all: the five folder commands became `#[tauri::command(async)]`, because a plain command runs on the main thread on macOS and a 5,000-file tidy froze the window for its whole length.

- **Slices 9b–9e scoped: folder sync across any number of members (2026-09-21).** Asked for as *"link folders in a set of already added destinations and keep them in step"*, with four behaviours named: mirror both, right sync, left sync and a 1-1 match that carries writes and deletes both ways, across two folders on one laptop or a laptop, a NAS, an FTP server and whatever connection schemes come later. Scoped now, in [09b-folder-sync.md](slices/09b-folder-sync.md), and scheduled after dedup and the watcher, because it needs the set-aside area the first brings and the change notification the second brings, and does not need the daemon. **The decisions, each argued in the brief:** a sync is a *set* of members and not a pair, since a set has one desired content per path where pairs would have several baselines that can disagree; the four behaviours are two knobs, `--push | --pull | --all` and `--exact`, with an anchor for the one-way forms, because four names hide two independent choices; **a leg is a link**, owned by the sync and hidden from the Links tab, so every rail the drain has earned is inherited without an engine change; the baseline is per member and **append-only**, its current value a query for the latest row whose plan is not undone, which is what lets `undo` retire a run's baseline with the same `undone_at` mark it already uses; a member is compared only with its own previous reading, never with another member, because clocks do not agree across backends (DESIGN §9) and FTP rounds to the minute; nothing is removed unless the sync's `on_remove` says how, default set-aside, and without `--exact` a hand deletion is copied back, so **`sync forget` is the one deletion that sticks**; conflicts are asked about in the window and parked unattended, named after the member they came from, and `newer-wins` is refused for the clock reason; and an empty member is never read as a deleted member, which is the failure every cloud sync client has shipped once and the reason for the two `--yes`-able refusals. **Two things this changes in DESIGN:** a new §4d records the subsystem, and the introduction's *"rclone / Syncthing (sync, not structure)"* is qualified rather than withdrawn, since a sync set is declared desired state of a second kind, the equality of several trees, and is previewed, journalled and reversible like the first. Not fixed here and worth a line: the table below still calls dedup *slice 8* while `docs/slices/08-the-redesign.md` has taken the number; dedup needs one of its own before it starts. The `15+` row gains the sync leftovers.

- **A file's history was unfindable by the path a person would type, and the fix was dead weight on Windows (2026-09-18).** `tungstate log` and `whereis` answered *"no matching operations"* for a file with a complete history. A row stores paths in whichever form the caller used when it was written — `folder add` canonicalises its root, a link does not — and on macOS `/tmp` and `/var` are both symlinks, so a folder governed as `/tmp/media` is stored under `/private/tmp/media` and asking about `/tmp/media/a.jpg` matched nothing. The failure is silent, because "no matching operations" is also the honest answer for a file nothing has touched. **Canonicalising the query is not the fix** — that breaks the reverse case, and an existing link test caught it immediately; neither spelling can be preferred, so both are tried. `resolve_for_lookup` does the resolving, and `canonicalize` alone will not do it either: the most useful question `whereis` answers is about a file that has *moved*, whose old path no longer exists and cannot be canonicalised at all, so it resolves the deepest ancestor that does exist and puts the rest back on. **Then Windows caught the fourth real bug of the project, twice in a row.** `canonicalize` there answers with a verbatim path — `\\?\C:\media` — that no journal row is ever spelled as, so the fallback could never match on Windows: dead weight on a third of the platforms, silently. And the test's own expectation compared against a bare `canonicalize`, demanding the one spelling the fixed function deliberately does not produce. The lesson is narrower than "test on Windows": `without_verbatim_prefix` is a plain string function with no `cfg!` in it, tested both ways from a Mac exactly as `separators_as_slashes` already was — **that treatment should have been applied to the whole test and not only to the helper**, which is what cost the second red run.

- **Slice 7e: the seam was closed so the window can be redesigned without touching Rust (2026-09-18).** A redesign is cheap only if it needs no engine work, and by that test the seam had three holes. **Results crossed as prose.** `tidy_folder` returned `"moved 5 file(s)"`, and a window that receives a sentence can only print it — there is no way to show the *5* large, put an undo beside it, or word it differently, without changing Rust; a screen that cannot restyle its own results cannot be redesigned. `tidy_folder` and `put_back` now return counts, and the window writes the sentence (which incidentally fixed `file(s)`: it reads "Moved 2 files." now). `already_tidy` is a separate flag rather than `moved: 0`, because "there was nothing to do" and "it moved nothing" are different sentences and only the window knows which it wants. **Two capabilities were command-line only:** `learn_folder` and `compare_folder` are commands now, which is what lets a picker ask *what would this do to my folder* instead of describing a shape. **And the comparison logic was duplicated** — it moved into `tungstate_core::compare` so both surfaces answer the same question, and the move immediately surfaced a bug neither had shown alone: a learned policy globbing `Work/Clients/Acme/**` claimed files at any depth below and filed them one level up, **flattening `2023/` out of the policy whose whole promise is keeping the shape you have**. `**` crosses directories; the second glob arm is now the shape itself, one segment per level, matching at exactly the depth the shape describes. Worth recording *how* that escaped: the by-hand check had passed because the fixture was copied with `cp -R`, which does not preserve mtimes, so every file sat inside the 30-second cooldown — and a plan reports those as **left alone**. *Left alone because correct* and *left alone because too recent* print identically. The contract is written down in `docs/SEAM.md`, including the five safety properties a simpler UI must keep and the three gaps (tidy progress events, extended attributes, search at scale) that would be additions to the seam rather than changes to it.

- **Slice 7d: three more starting layouts, and a way to try them on (2026-09-18).** The 7b picker offers a sentence per layout, and a sentence describes a shape when the question is *what will this do to my files*. `tungstate folder compare` answers the second question: every layout planned against the folder with a real example destination each, and **the folder's own rules as the first row**, so every other line reads as a change from where you actually are rather than from nothing. It also answers a question the 7b picker could not ask at all, since that picker only appears for a folder with no rules. `removed` is a column on purpose — `downloads` against an organised folder reports fourteen directories removed, which is the number that would have warned somebody before 7b's walkthrough watched `documents` flatten a hand-made hierarchy. **One walk serves every layout**, which is safe because `classify` applies each policy's own `ignore` when it plans and not only when it walks, so a shared walk cannot leak one layout's ignores into another's answer: 412 files against 7 layouts in about a tenth of a second. The new layouts are `media` (the five-level `YEAR/APP/TYPE/EXT/SIZE-BAND` shape 7c proved out), `by-date` (year then month) and `by-source` (one directory per app, no inbox — an unrecognised file is left where it is rather than swept into a directory named for the tool's own uncertainty). **The starter-layout property tests turned out to be green and empty:** the snapshot they share leaves `mime` and `mtime` unset, so `media` matched nothing against it and settled *vacuously* — four passing tests over zero coverage. A second fixture with real media types and dates now backs the new tests. The window still shows four cards and still only for a folder with no rules; that is 7e.

- **Slice 7c inserted: a folder's own shape can be read back out of it (2026-09-18).** Every slice until now runs one way — rules in, plan out — which is right for a folder with no shape and wrong for the folder most people have. Slice 7b's walkthrough made the cost concrete: pointed at a folder with four levels of hand-made structure, the `documents` layout planned `Work/Clients/Acme/2023/invoice.pdf -> PDF/2023/invoice.pdf`, dumped a curated `Personal/Photos/Japan 2023/` into `Unsorted/`, and `rmdir`'d `Personal`, `Projects` and `Work`. Every canned layout does this, because every one describes a shape rather than reading one. `tungstate folder learn` reads the shape and writes it down as an ordinary policy. **The design problem is one dimension:** in the target shape `YEAR / APP / TYPE / EXT / SIZE-GROUP`, four levels are computable from the file and *app is not* — nothing inside `IMG-20240312-WA0001.jpg` says WhatsApp. The `parent` attribute cannot carry it, because after the move the file's parent is `under-100MB` and the rule chases itself one directory deeper every run; **a `{parent}` rule never settles**. So a name becomes a literal in the path plus a two-armed glob in the match (`["WhatsApp/**", "**/WhatsApp/**"]`), the second arm being what makes the rule match its own output. The kind stays in `mime` rather than the glob, which is what lets a file arriving loose in `WhatsApp/` be filed as a photo before it is in a `Photo` directory. That claim was checked by hand — policy written, applied, re-planned to `0 file(s) would move` — before any inference was written. **Two bugs only running it could find:** asking each level for its values and taking the cross product wrote `path = "Personal/Personal/Personal"`, because two name levels are a tree and not a product (the unit tests were green, on the yardstick shape, which has exactly one name level — the width at which a tree and a product are the same thing); and the generated policy inherited an `inbox` from the canned layouts, which would have swept the 13 of 18 files the learned shape does not explain into `Unsorted/` — from the policy whose whole promise is keeping what you have. A learned policy now writes no inbox and leaves what it did not explain alone. Slice 8 (dedup, `on_duplicate`, `Trash`) is unaffected; the window's fifth layout card is 7d.

- **The index left slice 6, and the planner's op set shrank to four (2026-09-16).** Slice 6 was *index + scan + planner + `plan`*. The index is a cache, and a cache earns its keep from hits: nothing reads one incrementally until dedup (slice 8) wants *find all files with hash X* and the watcher (slice 9) wants *what changed since*. Building it now would ship the whole of cache invalidation three slices before its first reader, in exchange for nothing — and `Policy::required_tier()` already means a plan over a video library is stat-tier, a directory walk with no reading at all. It arrives as `tungstate-index` when something reads it. The walk moves to `tungstate-backend` instead, where `read_dir`'s own docstring was already pointing (*"a single directory is bounded, so collecting it is honest; recursive walks need streaming"*), which costs no new crate and no new dependency. Separately the op set came out at four — `MkDir`, `Move`, `Quarantine`, `RmDir` — against DESIGN §4's nine, and the interesting omission is `Trash`: see the next entry.

- **`on_conflict = "replace"` quarantines rather than trashes, and DESIGN §5 is amended (2026-09-16).** §5 said `replace` sends the existing file to the trash. The shipped drain had already decided otherwise and argued it in a comment — *"Replace is the user's decision about which copy they want, not permission to destroy the other one"* (`crates/tungstate-transfer/src/lib.rs:952`). `--on-conflict replace` on a link and `on_conflict = "replace"` in a policy are the same word offered to the same person about the same situation, so one of them would have been lying. The drain's reading wins because it is shipped, argued, and the safer of the two. The dividend is out of proportion to the change: with no `Trash` and no `Delete`, **no operation a slice-6 plan can express removes content**, so DESIGN §1's *no content is ever lost* becomes trivially checkable rather than carefully checkable, and a plan-only slice never has to reason about the OS trash, remote `.tungstate-trash/`, or retention. `Trash` arrives in slice 8 with `on_duplicate`, when an executor exists to honour it. **DESIGN §4's `observe` mode is amended in the same slice** to read *never applies* rather than *never plans*: reporting drift is planning, since the only way to know a file is misplaced is to compute where it belongs, and honouring the literal wording would make the safest command in the product the most restricted one while leaving everyone on the default mode unable to see their drift at all.

- **Slice 5b's tour was written after the fact, and slice 5c got a row (2026-09-16).** The brief promised `05b-tour.md` and it was never written, making 5b the only shipped slice without one — which quietly skips step 3 of the loop and leaves step 4, *the user reads the tour and the diff and says go*, with only the diff. Written now, before slice 6 starts, rather than folded into the next tour: a tour covering two unrelated slices teaches neither well, and the 5b code is what is being exercised by hand right now. The same brief promised a **5c** (`explain` and `policy validate` in the window, read-only) that the table had no row for; it is now scheduled after slice 7, which is where the 5b brief's own argument puts it — a policy screen is better designed once the planner and the executor exist and a policy is a decision something acts on.

- **The macOS app shipped without a bundle signature and macOS called it damaged (2026-09-15).** Reported as *"Tungstate.app is damaged and can't be opened"*, which is not the message the release notes prepared anyone for — they described the unidentified-developer prompt and told people to right-click → Open, which does not clear this one. Inspecting the released DMG showed why: `Signature=adhoc, linker-signed`, `Info.plist=not bound`, `Sealed Resources=none`. The *binary* carried the ad-hoc signature the Rust linker applies on arm64; the *bundle* had never been signed at all, so there was no `CodeResources` and `spctl` complained that "code has no resources but signature indicates they must be present". That combination is what Gatekeeper reports as damage. Fixed with `bundle.macOS.signingIdentity: "-"`, which makes the bundler ad-hoc sign the whole bundle before building the DMG; the identifier becomes `dev.tungstate.desktop` instead of a linker-generated name, the `Info.plist` is bound, resources are sealed, and `codesign --verify --deep --strict` passes. Still not notarised, so Gatekeeper still refuses on first open — but as an unknown developer, which the notes already explain, rather than as a corrupt download, which cannot be worked around at all. Verified by building the bundle locally and reading `codesign` before and after. Incidentally this disproves the slice 4e note that a local `tauri build` does not work: it builds fine, and the missing signing identity was most likely the original complaint.

- **Three UI bugs that shipped because nobody looked (2026-09-15).** Slice 5b's screens compiled, type-checked and passed every test, and all three of these were visible within a minute of actually opening the window. The 4d lesson, restated: *compiles and launches is not a done bar for anything with a screen* — and this time it was not even launched.

  **A `v-if` in the middle of a `v-if`/`v-else-if` chain.** The saved-link preview modal was inserted between `StorageView` and `LinksView`, which silently re-chained `LinksView` and `ConnectionsView` to the modal instead of to the onboarding branch. Both then rendered *underneath* the welcome panel rather than instead of it. Vue cannot warn, because a `v-if` is a legal neighbour for a `v-else-if`. Overlays now sit after the tab chain beside the other modals, where they always belonged.

  **A field with no `type` attribute is not `input[type="text"]`.** The stylesheet listed the types it wanted; an `<input>` written without one is a text field in every browser and matched nothing, so the Find screen drew a white box on a dark sheet and three more in the add-a-link dialog. The selector now excludes the two types that must not look like text boxes rather than listing the ones that must, which is the form that cannot be forgotten at a call site. Second time this exact rule has bitten: slice 4e fixed `input[type="password"]` the same way and did not generalise it.

  **`.opt` is a grid that stretched its rows.** Two side by side in a `.pair` grow to the taller one, and the spare height was shared between label and field, so a column without a note under it sat its dropdown lower than its neighbour. `align-content: start` holds the rows to their own height.

  Found by running the app against a throwaway journal and reading screenshots, tab by tab. Worth doing before saying a screen works, and worth doing again next slice.

- **A conflict prompt stalled the whole run, and narrowing had made that worse (2026-09-15).** Both found by using it. Two bugs that compounded, and the second is the interesting one.

  `WindowResolver::resolve` always emitted a prompt, treating the transfer dialog's conflict setting as a *fallback* for when nobody answered. But the dialog labels those options as decisions — "keep both, renaming the arriving file", "leave that one here" — and only quarantine as "ask me, and set aside if I am away". So choosing an action and then being asked about it contradicted the words on screen, and because every prompt holds a worker until it is answered, an unattended drain stopped at the first clash and waited. The command line had the same hole from the other side: `link run x` on a terminal prompted regardless of the link's stored rule. The rule now lives on `ConflictAction::wants_asking`, in the journal, read by both, so they cannot come to different conclusions about one setting.

  The governor made it fatal rather than annoying. Narrowing stopped at one worker, and with one worker a single prompt halts everything rather than one file of it. **The measurement was not wrong** — on a saturated link one worker genuinely moves as many bytes as four, so "narrower is no slower" was true every time and it walked all the way down. What bytes per second cannot see is that a run of one has no redundancy: any single blocking thing, a prompt most obviously but equally a slow rename or a stalled socket, stops all of it. So `Limits` gained a `minimum` of two, and narrowing stops there. An explicit `--parallel 1` is still honoured, because asking for one is different from arriving at one. Three of slice 4g's tests changed to match, deliberately and with the reason written into them.

- **Storage: export, import, archive and a reset that is not a cliff (2026-09-14).** Asked for as "a reset storage button so we can have a truly clean slate". Built as something safer than that, after two rounds of the user improving the design. The first proposal archived the SQLite file; the user's objection killed it — *"a journal.db file would be useless to a non-technical user"* — and the second version was theirs: **JSON, so it can be scripted against and can cross a schema change no migration could span.** The document carries two version numbers, the format's own and the schema's, because they answer different questions and a future build with an incompatible schema still has to be able to read an old export. **The tables are read by reflection rather than from a hand-written list of columns**: `SELECT *` plus the statement's own column names, so a column added in a later slice is exported and imported without anyone remembering to come back, and a test asserts every column the database has appears in the export. Reset archives first and clears rows rather than the file, so there is no window in which the journal does not exist. Restore archives what is there first, making it reversible in its turn. Both refuse while a run has left work behind, because those rows are the only thing that knows a part-copied file exists at the far end. Passwords are deliberately absent from an export and stay in the keychain, which also makes restore work: the keychain key derives from the connection name, so a connection restored under its own name finds its password again. **The bug this nearly shipped with:** archive names were second-resolution, and a restore archives the current journal immediately after reading the one it is restoring, so the second write landed on the first. Caught by a test asserting the two names differ; names are now never reused.

- **`tungstate log <absolute path>` had never worked on Windows (2026-09-14, found in slice 5b).** Caught by CI, on a test written for something else entirely. A journal row keeps its root and its path in separate columns, and `history` and `whereis` join them with `/` to compare against what the caller typed. On Windows the stored root is `C:\Users\me\dst` and the caller types backslashes throughout, so the comparison was against `C:\Users\me\dst/a.mp4` — a spelling nothing produces. It matched nothing, silently, and answered "no matching operations" rather than failing. Fixed by normalising both sides to forward slashes, **on Windows only**: on Unix a backslash is an ordinary character in a filename, and normalising there would make `a\b.mp4` and `a/b.mp4` compare equal, which is two different files answering to one name. The platform is a parameter rather than a `cfg!` read inside the functions, so both answers are tested from either machine, and the generated SQL for both is prepared against a real database in the same test — a syntax error in the Windows branch is otherwise invisible from anywhere but a Windows CI run. Third time Windows has caught a real bug in this project.

- **A transfer can be added to one already running, and two command-line runs no longer collide (2026-09-14).** Both asked for after using the thing. The window refused a second Move with "a transfer is already running", because `spawn_run` moved its list of links into the worker thread and nothing could reach it afterwards; the list now lives in a `RunQueue` the worker pops from, so a Move during a run joins it instead of being turned away. The correctness argument is one sentence and is why the queue and the "is a worker running" flag are one type rather than two fields: a worker only ever clears the flag while holding the queue's lock, so it cannot decide it has finished in the gap between a submission pushing and that submission checking whether to start one. There is a test that runs four submitters against a constantly-draining worker and asserts every item comes out exactly once. The window also had to learn the difference between starting and joining, because it blanks the progress list when a transfer begins and doing that to a run in flight would erase the live view of the thing the files just joined. Separately, the journal gained a five-second busy timeout: WAL allows only one writer, and without it a second `tungstate link run` in another terminal got `SQLITE_BUSY` the instant it collided rather than waiting. **Not the daemon.** A queue that survives the process, or that a second process can push into, is still slice 10; this is the in-process version and goes no further.

- **`OpenDAL` writes every FTP temporary file at the connection root (2026-09-14).** Found by draining to the NAS, and misdiagnosed twice before the wire log settled it. `build_tmp_path_of` is `get_basename(path)` plus a random suffix, so the directory is dropped and never put back; the temporary file is created at the connection root and only the closing rename puts it right. A writable root hides it, which is why the Docker integration tests pass. A Synology root is the virtual shared-folder list — it lists perfectly and accepts nothing — so all 65 files failed with `553 <name>: Permission denied`, naming only the basename because the basename was all that was sent. Append mode would use the path as given and is advertised, but its `close` returns no content length and `CompleteWriter` rejects it, so both routes through the `Operator` API are wrong. Recorded in DESIGN §6; the real fix is upstream or a hand-rolled write path. What ships here is that the question gets asked once: `probe_writable` writes one byte to the root and takes it away, `connection test` reports it, and a root that refuses files says so along with the remedy instead of failing every file separately. **The lesson is about the test, not the bug:** the integration suite pointed its connection at a writable home directory, so the one property that mattered was the one it could not see.

- **A connection saved without a root wrote to the server's own `/` (2026-09-14).** Found by draining to the NAS over FTP, not by a test: every one of 65 files came back `553 Permission denied` with `written: 0`. `OpenDAL` normalises an empty root to `/`, so the connection was writing to the NAS's real filesystem root rather than into the share; the account could list it, which is why `connection test` passed and said "reachable". The trap was already named in `tests/ftp.rs` — *"a root of `/` is the machine's real root, which the account cannot write to. Getting this wrong is the first mistake anyone will make"* — and the product then let it be made silently, because `--root` is optional and the failure surfaces one file at a time as sixty lines of protocol context that never mention the field that is wrong. Three fixes, none of them a new refusal: `Scheme::rootless_warning` is one rule in the journal that the CLI's `add`, `update` and `test` and the window's connections table all read, so the two surfaces cannot disagree; and a refused remote write now leads with what to check instead of with `ErrorKind::Unexpected`. Deliberately a warning rather than an error, because `/` is genuinely right on a server that chroots the login, and which one you have is not something tungstate can know.

- **Precedence became first-match-in-file-order, and `priority` is gone (2026-09-14, slice 5).** DESIGN §2 originally specified most-specific-match-wins with a `priority` tiebreak and a load-time ambiguity error. A specificity metric over globs, regexes, mime wildcards and size ranges is a heuristic dressed as a rule, and file order is the one ordering every reader already understands. What makes the simpler rule safe is the user's argument, recorded in §2 because it is the load-bearing part: reconciliation is convergent, so a mis-ordered rule is not a permanent mistake — reverting the rule reverts the structure, the way a revert does in git. That is what Hazel and friends cannot offer, and it is why the usual objection does not land here. A **shadowing warning** replaces the ambiguity error: a rule that can never fire is named along with the rule that shadows it, exactly for literal `ext`/`mime` sets and intervals, and silently when globs or regexes are involved.

- **`tungstate-attrs` exists as a separate crate so core stays I/O-free (2026-09-14, slice 5).** DESIGN §7 puts the policy model, classifier and planner in `tungstate-core` and calls its having zero I/O "the load-bearing decision for testability". Gathering a file's attributes is I/O by definition, so it could not live there. The split keeps the promise: the whole classifier is property-tested with no filesystem, and `tungstate-attrs` owns the extractors and the tier budget. `Backend` gained a defaulted `read_prefix` in the same slice, for the same reason slice 4f used one — six existing implementations kept compiling, and the default is correct rather than a stub, so a backend that cannot do ranges is slow and never wrong.

- **The FTP tier saving is real but not exact, and the tests say so (2026-09-14, slice 5).** Against a 658 MB video on a real vsftpd: a `stat`-tier policy caused no data transfer at all, a `head`-tier one (8 KiB asked) moved 1.1 MB, a `meta`-tier one (64 KiB asked) moved 1.6 MB. FTP has no way to request a range with an end — `REST` sets a start, and ending a `RETR` early means closing the data connection after the server has pushed its socket buffers. So over FTP a tier bounds what is *requested*, not what arrives; over HTTP, S3, WebDAV and SFTP the range is exact. The FTP test asserts the file did not come across rather than a byte count that belongs to the kernel, on the principle that a test asserting more than the system promises fails for a reason nobody can act on.

- **Bucket labels are spelled in words (2026-09-14, slice 5).** `<10MiB` is not a legal directory name on Windows or over SMB, and sanitising `<` and `>` to `_` would put `<1GiB` and `>1GiB` in the same folder — a silent data-merging bug born of a cosmetic rule. Policies are still written `["<10MiB", "10MiB-1GiB", ">1GiB"]`; the labels derived from them are `under-10MiB`, `10MiB-1GiB`, `over-1GiB`, and a test asserts each survives `sanitize` unchanged.

- **The rolling release tag moved from `main` to `rolling` (2026-09-14).** Git resolves `refs/tags/` before `refs/heads/`, so a tag named `main` shadowed the branch: `git log main`, `git diff main` and `git rebase main` all silently targeted the last rolling build instead of the branch head. Harmless while every slice lived on its own branch; not harmless now that work lands directly on `main`, which makes those daily commands. Releases still fire on every green push to `main` — only the tag name changed. The five slice branches and the last PR branch were deleted at the same time, all of them already ancestors of `main`.

- **The window learned `TUNGSTATE_JOURNAL`, and slice 4e got its walkthrough (2026-09-12).** The desktop app called `Journal::open_default()` with no override, so exercising it by hand meant writing connections and links into the real database on the machine doing the exercising. It now honours `TUNGSTATE_JOURNAL` exactly as the command line has since 4b, and for the same stated reason. That plus `TUNGSTATE_SECRET_<NAME>` is what made an automated walkthrough possible against a throwaway journal, a throwaway `HOME` and a Docker FTP server, with nothing written to the real keychain — verified afterwards by looking. The walkthrough covered: the add dialog and its FTP warning, the derived "sends your password in the clear" marker, `Test` reporting the root with the count, `nas:` in each pane's "Go to…", browsing a connection with Up correctly disabled at its root, a preview and a 480 MB drain over FTP checked against the server afterwards, editing a root and confirming in SQL that the link row was untouched while the connection moved under it, and a refused sign-in reporting credentials rather than the network. It found one defect, below. The one step it could not force was killing a run mid-flight: a loopback FTP server drains 480 MB faster than the process can be killed, and that path is covered by `an_interrupted_drain_over_ftp_resumes_and_sweeps` in the FTP suite.
- **The connections table broke an address in half (2026-09-12).** Found by the walkthrough above, in the one state no test rendered: a failed check. The Where and Folder cells used `.path`, whose `word-break: break-all` is right for a file path and wrong for a token, so the first sentence-long error in the column beside them reflowed `127.0.0.1:2121` into `127.0.0.1:2 121`. They get their own rule now, and the check column is capped so a long failure wraps inside itself instead of starving its neighbours.

- **A rolling `main` build, so there is always something installable (2026-09-12).** Releases were tag-only, which meant testing the app as built meant either cutting a version or building it locally — and the local `tauri build` is the one that does not work. `release.yml` gained a `workflow_run` trigger on CI, so every commit that goes green on `main` refreshes a `main` prerelease carrying the same artefacts a real release does. Gated on CI rather than on the push, because a build that compiles and fails its tests is exactly the build nobody should install; and it checks out the commit CI *tested* rather than the current head, because another merge can land between the two runs. It reuses `release.yml` instead of getting its own workflow so that what you test from `main` is built the same way as what you release. The publish job also gained a completeness check: the desktop artefact upload has to use `if-no-files-found: warn` (its paths list every platform's bundle and only one matches per runner), so a stale bundle path would empty the desktop half of a release in silence — now it fails the publish instead.

- **The narrowing tests measured the scheduler, not the governor (2026-09-12).** Slice 4g's ramp-down tests slept for a real 40ms window and let the wall clock answer. `sleep` may overshoot by any amount; an overshoot collapses the measured rate below the 95% keep-ratio; and one collapsed window sets `Trend::Settled`, which is permanent by design — so narrowing stalled and never resumed. It failed on macOS CI as `left: 3, right: 1`. `Governor` gained a `reconsider_after(moved, elapsed)` seam alongside `reconsider`, so the tests supply the duration instead of sleeping through it; the production path still reads the clock, and `nothing_is_decided_before_a_full_window_has_passed` still exercises it. The tests are now deterministic (150/150 under CPU load, where they had been failing intermittently) and instant. The principle restated: a test that sleeps is a test that asserts on the machine it happens to run on.

- **`quarantined` read the wrong filesystem (2026-09-12).** The desktop app's `quarantined` command built `link.destination.path.join(".tungstate-quarantine")` and walked it with `std::fs`. For a remote link `destination.path` is a *connection-relative* path, so that resolved against this machine's working directory, found nothing, and returned an empty list — "nothing is set aside" however many files were. The read now lives in `tungstate-transfer` next to the code that writes quarantine, takes the destination backend, and reuses the existing `walk::files_under`. It also asks by listing rather than by `stat`, so "nothing is set aside" and "the destination cannot be reached" stay different answers; an unreachable NAS is an error, not an empty list. Latent rather than live — the command is registered but no screen calls it yet — and deferred out of 4d and 4e before being fixed here.

- **Slice 4e grew `connection update` and `connection password` (2026-09-12).** The window gained an edit dialog, and the CLI is the reference surface — it must not be able to do less than the window, or the two disagree about what a connection can be. `password` turned out to be a missing recovery path rather than a convenience: `BackendError::Auth` tells you to re-enter the password, and until now there was no way to, because `connection remove` is refused while any link points at the connection. The journal API that backs both encodes the one thing that is *not* editable — `ConnectionSettings` has no `name`, because the name is the link-spec token and the keychain account, so a rename is two migrations wearing one hat.
- **The flaky FTP CI job fixed inside slice 4e (2026-09-12).** Not a regression: green on `slice-4d`, red on `slice-4f`, green on `slice-04-concurrency`, red on `main`, with no code change to explain any of it. The image creates the FTP account before its home directory, and the workflow repaired that in a step *after* a readiness poll that only checked login — but a login can succeed in the window before the root is listable. Fixed at the root twice over: a bind-mounted host directory makes the home exist before the container does (so the repair step is deleted rather than tuned), and the poll now LISTs the root over a passive data connection, which is what the suite's first call does. The push trigger also gained `fix-**`, because slice 4g shipped on such a branch and so never got a three-platform run at all.
- **The endpoint helpers moved from the CLI into the journal (slice 4e).** `describe` and `place` were byte-identical in `cli/src/ends.rs` and `gui/src/main.rs`, and 4e would have added a third copy. They moved with `parse_end`, `connection_prefix` and `EndError` to `tungstate-journal`, which owns `Endpoint` and `Connection` and which `parse_end` already needed a handle to — so the move cost the journal no new dependency. Two helpers joined them for what the window needs and the CLI never did: `join_display` and `parent_display`, because `Path::join` yields `nas:inbox\a.mp4` on Windows and `Path::parent` on `nas:inbox` answers `Some("nas:")` where the honest answer at a connection's root is `None`.

- **Per-file resume rather than byte-offset, in slice 3.** Everything committed is kept and only the file in flight is redone. Byte-offset resume moves to slice 4c or later, where FTP makes partial transfers genuinely expensive; over a mounted volume the code to track and validate partial writes carries more corruption risk than the minutes it saves.
- **Slice 4f inserted (2026-09-11).** Found by using 4d rather than testing it. A link recorded its two roots and not which files the user picked, so a selection lived only in a worker thread and died with the process. Three symptoms, one cause: an interrupted batch could only report the one file that had started, a resumed run re-walked the whole source folder instead of the batch, and no queue could be shown because none existed outside a running process. Migration v5 stores the selection; "no rows" keeps meaning the whole root, so saved folder-pairs and every existing link are unchanged. "Progress events" moves out of slice 4 into here, leaving slice 4 as concurrency, bandwidth caps and reachability pausing.
- **Slice 4d inserted, connections moved to 4e (2026-09-11).** Unplanned, and found by using the desktop app rather than by testing it. A one-off browser transfer makes an unsaved link, `links()` hides unsaved links, and recovery is scoped per link — so an interrupted browser transfer was unreachable and its partial orphaned on the destination for ever. Two other bugs in the same session: Tauri resolved an empty ACL so the window could not hear any engine event, and the Activity view used five class names the stylesheet does not define. The lesson recorded: "compiles and launches" is not a done bar for anything with a screen.
- **Slice 4b split into three (2026-09-11).** What was one "OpenDAL FTP backend" slice became the seam (4b), FTP (4c), and the desktop app's connection screens (4d). The seam is the part that touches every crate and needs a schema migration, and it can be proven on all three CI platforms with no network at all by running the existing transfer suite through OpenDAL's own `fs` service. Shipping it first makes FTP a service registration plus its quirks rather than a rewrite.
- **SFTP leaves OpenDAL (2026-09-11).** OpenDAL's SFTP service is Unix-only, refuses password authentication, and delegates host-key checking to the system `ssh` client — contradicting three-platform support, password auth for a consumer NAS, and tungstate-controlled trust-on-first-use. It will be hand-rolled on `russh` + `russh-sftp` behind the same `Backend` trait. Recorded in DESIGN.md §6; implemented much later.
- **The engine gained a commit path that does not rename (slice 4c).** `Capabilities::atomic_rename` was defined in slice 1 and read by nothing until FTP, whose OpenDAL service answers `rename` with `Unsupported`. Without rename the only route to the final name is to write to it, so `copy_verify_commit` branches and recovery follows. `ConflictAction::Replace` is refused on such a destination, because moving the existing file aside is the promise it cannot keep. S3 and WebDAV need the same path in slice 12.
- **An old binary can no longer open a newer journal (2026-09-11).** Schema v4 makes a link end relative to a connection, so a build that does not know about connections would read a remote path as a local one. `migrate` returns `JournalError::TooNew` rather than skipping. Recorded in DESIGN.md §4c.
- **Links are stored in the journal database, not a config file.** A link's definition and its progress then update together, and a resumed drain finds its own interrupted work by link id. This widens the journal crate from provenance to persistent state.
- **Network-mount detection moved out of slice 1 into slice 4.** Reading `MNT_LOCAL` on macOS or `GetDriveType` on Windows means either `unsafe` FFI, which the workspace lints forbid, or a heavy dependency. It is also a poor second lesson in Rust. Nothing needs it until slice 4 picks a default verification level per link. Slice 1 instead discovers hard-link and case-sensitivity support by probing the filesystem, which is safe, portable, and more accurate than asking the operating system.
